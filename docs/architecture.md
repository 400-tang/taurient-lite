# Taurient Lite 整体架构

写给想一次看懂「这个项目由哪些部分组成、数据怎么流动、每天到底发生了什么」的自己。
前端呈现层的细节在 [frontend-architecture.md](frontend-architecture.md)，这里讲全局。

---

## 一句话概括

**一条每天跑一次的数据流水线，加上两个把结果展示出来的出口。**

它不是一个「网站」，也不是一个「应用」。核心是一条流水线：
抓数据 → 模型判断 → 写成 JSON → 渲染成页面。
JSON 是唯一的真相来源，网页和 Markdown 都是它的衍生品。

---

## 五个组成部分

```
┌─────────────────────────────────────────────────────────┐
│  1. 数据采集层        跑在 GitHub Actions                │
│     Yahoo 行情、FINRA 空头持仓、全市场价量扫描           │
│     产出：data/*.json（提交进仓库）                      │
└──────────────────────┬──────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────┐
│  2. 判断层            跑在云端 Claude Code 定时任务       │
│     扫新闻、去重、分层、写「为什么重要」                  │
│     照着 RUNBOOK.md 执行                                 │
│     产出：briefs/YYYY-MM-DD.json  ← 唯一真相来源          │
└──────────────────────┬──────────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────────┐
│  3. 渲染层            taurient_lite/ 包，零第三方依赖     │
│     校验 JSON → 拼成 HTML 和 Markdown                    │
│     纯函数：同样的输入永远得到同样的输出                  │
└──────────┬───────────────────────────┬──────────────────┘
           ↓                           ↓
┌────────────────────────┐  ┌──────────────────────────────┐
│  4a. 静态出口           │  │  4b. 动态出口                 │
│  site/index.html       │  │  backend/ FastAPI @ Render    │
│  发布成 Artifact        │  │  现场渲染 + 实时行情 + 登录   │
└────────────────────────┘  └──────────────────────────────┘
```

外加第五部分：**测试**（`tests/`，326 个用例，零依赖，0.04 秒跑完）。

## 1. 数据采集层：为什么要用 GitHub Actions

这是整个架构里最反直觉的一个设计，但理由很硬。

**云端 Claude Code 定时任务跑在一个出站白名单沙箱里**——除了 Anthropic 自己的
API、包管理器源和 GitHub，别的目的地在 CONNECT 阶段就被网关拒绝。Yahoo 连不上，
自建的 Render 后端也连不上。

所以把取数的方向反过来：**让 GitHub Actions 的 runner 先把数据抓好、提交进仓库，
定时任务 clone 的时候数据就跟着下来了**，读文件即可，一次外网都不用发。
GitHub 恰好是沙箱唯一能连通的外部服务。

两个工作流，刻意分开：

| 工作流 | 时间 | 做什么 | 为什么这个时间 |
|---|---|---|---|
| `market-snapshot.yml` | 每个工作日 12:30 UTC | 抓行情和空头持仓，几秒钟 | 美东 8:30，开盘前一小时，拿到的是前一交易日收盘价 |
| `momentum-scan.yml` | 每个工作日 21:30 UTC | 扫 2500 只票的价量异动，一两分钟 | 美东 17:30，**收盘之后**，当天 K 线已经走完 |
| `momentum-scan.yml` | 每周日 09:00 UTC | 重建流动性名单，几千次请求 | 周末没人跑 |

**为什么分成两个工作流**：节奏不同。混在一起，慢的会拖累快的，任何一步失败还会连坐。

**为什么异动扫描排在收盘后**：原本排在开盘前 12:10，实测发现 GitHub 的定时任务
会延迟 4–6 小时（官方已知行为），于是扫描落在盘中，拿到的是还在变动的当天 K 线。
排到收盘后两头都解决了——当天 K 线已完整，即使再延迟几小时跨到凌晨，数据仍然
属于同一个完整交易日。

## 2. 判断层：模型做什么，代码做什么

这条分界线是整个项目的设计核心。

| 交给代码 | 交给模型 |
|---|---|
| 抓行情、抓空头持仓 | 扫新闻、判断哪条重要 |
| 价量异动的**数值计算** | 异动条目的**文字解读** |
| JSON 结构校验 | 同一事件跨媒体去重、合并 |
| 渲染 HTML / Markdown | 写「为什么重要」 |
| 所有可以被测试断言的事 | 所有需要判断力的事 |

原则很简单：**能写成确定性函数的，就不要让模型每天重新想一遍。**
`apply_momentum.py` 是这条线的典型——数字自动填进 JSON，判断留给人/模型写。

模型执行的流程写在 [RUNBOOK.md](../RUNBOOK.md) 里，五步：
扫描 → 筛选排序 → 写 JSON → 取行情并渲染 → 发布并归档。
RUNBOOK 同时是给人看的文档和给定时任务读的指令。

**定时策略**：cron 只认 UTC，单点触发会在夏令时切换时漂一小时。
所以排成每天两次 `0 13,14 * * 1-5`，由运行提示里的时间闸门决定哪一次真正执行——
只有加州本地时间已过 6:00 且当天简报尚未生成时才动手。夏令时命中 13:00 那次，
冬令时命中 14:00 那次，另一次空跑退出。

## 3. 渲染层：taurient_lite 包

零第三方依赖，只用标准库。分层严格向下，没有循环依赖：

```
schema.py        数据定义与校验（910 行）—— 不依赖任何模块
   ↑
config.py        读 config.json
theme.py         设计 token 与 CSS（1482 行）
components/      数据 → HTML 片段
   ↑
html_renderer.py / markdown_renderer.py    组装整页
   ↑
pipeline.py      编排：定位 → 校验 → 渲染 → 写盘
```

**流水线不做任何网络请求。** 取行情是 `quotes.py` 的事，发生在渲染之前，
结果写进简报 JSON。所以渲染永远是纯函数式、可重放的：同样的 JSON 一定得到
同样的页面。这也是测试能在 0.04 秒跑完 326 个用例的原因。

### 纯计算模块

这几个模块只吃数据、不碰网络、不做判断，可以单独测试：

- **`momentum.py`**（493 行）：价量异动判定。把票分成初动 / 延续 / 基底 / 已延伸
  四档，核心问题不是「谁涨得多」而是「走到这波的第几天」
- **`short_interest.py`**：FINRA 官方空头持仓
- **`quotes.py`**：行情抓取与解析，带重试
- **一目均衡表**：写过，两轮验证都没通过，**代码已删除**，结论留在下面的
  「失败的实验」一节

## 4. 两个出口

### 4a. 静态出口（主路径）

`python3 render.py` → `site/index.html` → 发布成 Artifact。
一个自带样式的 HTML 文件，零 JavaScript，没有构建步骤。

### 4b. 动态出口（backend/）

独立的 FastAPI 服务，部署在 Render，**直接 import `taurient_lite`，
不重新实现任何抓取或渲染逻辑**。它只解决静态页面做不到的三件事：

| 路由 | 解决什么 |
|---|---|
| `/` | 现场读最新 JSON 渲染，永远反映仓库里最新的数据，不用手动发布 |
| `/api/quotes/live`、`/api/quote/{ticker}` | 现场查 Yahoo，拿此刻的价格，不用等第二天 |
| `/api/short-interest/{ticker}` | 查任意股票的 FINRA 空头持仓，不限于固定名单 |
| `/api/search` | 按公司名搜代码（Yahoo + 官方名单合并，带容错） |
| `/api/brief` | 直接拿 JSON |

还有一个登录与个人自选股面板（`auth_panel.py`，661 行），用 Supabase 做账号：
邮箱魔法链接登录，自选股存在 Supabase 一张表里，行级安全策略锁死，谁都只能
读写自己那一行。登录后跟自己关心的股票有关的新闻会高亮，还能一键隐藏不相关的。

**这一层完全隔离在 `backend/` 里**：`taurient_lite/` 核心包对 Supabase 一无所知，
保持零依赖。渲染时每条新闻带一个 `data-tickers` 属性标出涉及哪些代码，
这个属性对 Artifact 版本完全无害，只有登录面板的 JS 会用它。

## 贯穿全局的几条设计原则

### 1. JSON 是唯一真相来源

网页和 Markdown 都从 `briefs/*.json` 生成。想换配色只改 `theme.py`，历史数据
不动；想改覆盖范围只改 `config.json`，渲染逻辑不动。数据和呈现彻底分开。

### 2. 核心包零依赖

`taurient_lite/` 只用标准库，`tests/` 也是。唯一需要装东西的地方是 `backend/`
（fastapi / uvicorn / httpx），它的测试也因此独立于主测试套件——主套件不能
因为后端需要 FastAPI 就连带装进每日流水线的运行环境。

### 3. 渲染是纯函数

不发网络请求，不读时钟，不依赖外部状态。所以可重放、好测试。

### 4. 依赖方向严格向下

每一层都能单独测试。改 `theme.py` 不会影响 `schema.py`。

### 5. 失败的实验留在仓库里

README 里同时保留了早期偏斜样本（59 只、153 次信号）和全量回测
（2515 只、5090 次信号）两组**结论相反**的数字，因为犯错的过程本身是结论的一部分。

### 一目均衡表：试过，没通过，已删除

引入它本来是为了补 `momentum.py` 缺的一个维度——**上方阻力**。突破判定只
回答「有没有创出新高」，回答不了「创出新高之后头顶还有没有东西压着」。
云（Kumo）向前投影 26 天，是少数能提前给出未来阻力位的指标。

两轮验证，两轮都没通过：

**第一轮，用一目筛选初动信号的质量。** 5266 次初动信号、20 日前向收益。
云的位置没有信息量——能创出 50 日新高的票，98.5% 本来就在云上方（云上 5186、
云中 79、云下 1）。云的位置和「突破 50 日高点」这个已有条件几乎完全重合。

**第二轮，用一目在基底档提前预告突破。** 611,874 个基底档交易日，预测
「未来 20 日内进入初动档」，基准命中率 6.43%。单看很漂亮：云上 11.12%（1.73x）、
TK 金叉 10.02%（1.56x）。但朴素基准「离 50 日高点还差多少」更强：差 <2% 命中
15.15%（2.36x）。

决定性的是控制变量之后：只看已经离突破位 5% 以内的 76,857 个观测（该组基准
13.28%），云上 13.85%（**1.04x**）、TK 金叉 13.84%（**1.04x**）。**一目那些看
起来很强的预测力，几乎全部是「价格离前高很近」这一件事的另一种说法。**

结论不是「一目没用」，而是**「一目在这两个用途上被一个更简单的指标完全覆盖」**。
这两句话不一样，后者才是可以据以决策的。将来若要重新引入，得先想清楚它被用在
哪个**不与突破条件重合**的位置上。

这条在学术和工程上都值得保留：**记录什么行不通，和记录什么行得通一样重要。**

## 一天的完整时间线（UTC）

```
09:00 周日   重建流动性名单（GitHub Actions）
12:30 工作日  抓行情 + 空头持仓 → 提交进仓库（GitHub Actions）
13:00/14:00  云端 Claude Code 定时任务启动
             ├─ 时间闸门判断：本地是否已过 6:00？今天是否已生成？
             ├─ 扫新闻（≥12 组查询 + 逐个自选股）
             ├─ 去重、分层、写 JSON
             ├─ 读 data/ 里的行情和异动快照，填进 JSON
             ├─ render.py → site/index.html + briefs/*.md
             └─ 发布到 Artifact，提交回 GitHub
21:30 工作日  收盘后扫描全市场价量异动 → 提交进仓库（GitHub Actions）
             （供第二天早上的任务读取）
```

## 常用命令

```bash
# 渲染
python3 render.py                           # 最新一份
python3 render.py 2026-09-10                # 指定日期

# 数据
python3 fetch_quotes.py                     # 取行情
python3 snapshot_market.py                  # 行情 + 空头持仓快照
python3 scan_momentum.py                    # 全市场异动扫描
python3 scan_momentum.py --limit 200        # 本地调试，只扫 200 只
python3 scan_momentum.py --refresh-universe # 重建流动性名单
python3 apply_momentum.py 2026-09-10        # 扫描结果写进简报
python3 fetch_short_interest.py TSLA        # 查 FINRA 空头持仓

# 测试（改完 taurient_lite/ 下任何文件都要跑）
python3 -m unittest discover -s tests -t .  # 326 个用例
python3 -m unittest backend.test_server -v  # 后端测试，需要 FastAPI

# 后端本地跑（必须在仓库根目录）
uvicorn backend.server:app --reload

# 生成今天的简报
claude "照着 RUNBOOK.md 生成今天的简报"
```

## 想改东西时去哪儿

| 改什么 | 改哪里 |
|---|---|
| 配色、字体、版式 | `taurient_lite/theme.py` |
| 页面结构、某个板块 | `taurient_lite/components/` |
| 板块顺序、标签页 | `taurient_lite/html_renderer.py` |
| 自选股、覆盖范围、条数目标 | `config.json` |
| 简报的字段定义与校验规则 | `taurient_lite/schema.py` |
| 异动判定的阈值 | `taurient_lite/momentum.py` |
| 模型每天执行的流程 | `RUNBOOK.md` |
| 定时任务的时间 | `.github/workflows/*.yml` + 云端 routine |
| API 路由 | `backend/server.py` |
| 登录与个人自选股 | `backend/auth_panel.py` |

**不要直接改 `site/index.html`**，它是产物，下次渲染就被覆盖。
